# Acceptance Checklist

Scope: Explicit offline renderer operation or implementation. Enter through [Offline workflow](offline-workflow.md) for the local runtime contract.

Record pass/fail evidence for every item. A failed blocking item prevents delivery.

## Asset Integrity

- [ ] Every uploaded file has a manifest entry.
- [ ] Every upload has one resolved source role and preservation level.
- [ ] Every `reference_only` asset has an explicit, human-reviewed `influenceScopes` array, including `[]` when no influence is approved.
- [ ] At least one `product_core` asset is approved as `must_use_exact` before production continues.
- [ ] Observed, user-supplied, inferred, and unknown claims remain distinguishable.
- [ ] Duplicates are grouped and a canonical source is identified.
- [ ] Every `must_use_exact` asset is present once unless the user approved repetition.
- [ ] In `merge_all`, every ID in `requiredVisibleAssetIds` appears exactly once and every uploaded and approved content image makes a visible, auditable contribution.
- [ ] Filename guesses, duplicate hashes, and UI-looking pixels did not silently reduce the approved visible count.
- [ ] No `reference_only` asset appears as visible content.
- [ ] Every reference influence is represented by one VisualDirection v6 `referenceInfluencePlan` entry bound to that asset, an approved scope, and observed or user-supplied evidence.
- [ ] Reference influence is limited to `layout`, `palette`, `lighting`, `material`, `texture`, `typography`, and `motif`; unlisted influence axes are prohibited.
- [ ] Products, logos, exact museum images, and exact text match their source hashes.
- [ ] Every `cutout` carrier has decoded source transparency; every opaque source uses a truthful physical carrier.
- [ ] Every required visible source has exactly one closed `representation`, and references receive no representation.
- [ ] Exact products, logos, and approved text remain exact; they are not converted into drawings, fields, overlays, or reliefs.
- [ ] Every derived `technical_drawing`, `material_field`, `tracing_overlay`, or `relief_impression` binds a `can_transform` source to explicit user-supplied transformation evidence.
- [ ] Representation form, carrier, `materialFamily`, render strategy, and light behavior are compatible and remain in the closed VisualDirection v6 vocabulary.
- [ ] Every representation binds transformation and scale evidence to its own asset; unknown material or scale remains labeled `unknown`.

## Layout and Text

- [ ] The chosen template ID and seed are recorded.
- [ ] Same inputs produce byte-equivalent `SceneSpec` JSON.
- [ ] No visible object is outside the safe canvas.
- [ ] No protected product is materially occluded.
- [ ] Every required contribution meets `minimumVisibleShortEdgePx`; an impossible fit stops through `adapt_or_block`.
- [ ] Hierarchy contains one hero and supporting/contextual contributions rather than equal visual weight.
- [ ] `layoutRouting` records the evidence-backed surface style and actual selection signals, then contains each supported template exactly once with three distinct route signatures.
- [ ] Every candidate `compositionGrammar` begins at that hero, covers every required source once in reading order and once in one contiguous authored group, and gives every non-hero source exactly one earlier parent.
- [ ] Archetype, count, alignment, scale rhythm, flow, and required group role are compatible; EDC-style `modular_inventory` is used only for a real inventory relationship.
- [ ] The grammar is rooted and relative-only: no `x`, `y`, region, millimetre, hidden anchor box, disconnected corner stamp, or equal-card dashboard is present.
- [ ] Edge touch and shallow overlap use tight spacing; hero overlap is absent, and any allowed shallow overlap names only its approved non-hero pair.
- [ ] The negative-space strategy remains coherent and tools appear only when approved and necessary; a sparse tool-free scene is valid.
- [ ] For one-to-six visible sources, every large gap is classified as `functional_breathing_space`, `recoverable_by_recomposition`, or `supplement_candidate`; existing sources are recomposed and their optical centroid is brought near the safe-field center before any addition is proposed.
- [ ] Every supplementary option is P3/P4, is shown to the user with purpose, material/form, approximate candidate area, relative scale, and removal impact, and remains absent until explicit user selection. A selected new source returns the changed manifest to the first human approval.
- [ ] The three candidate scenes are materially distinct, not seed-only or decoration-only variants.
- [ ] All text fits at or above minimum font size.
- [ ] The visible-text inventory equals the approved Text Intent Gate allowlist.
- [ ] No exact text was generated by an image model.

## Lighting and Materials

- [ ] Exactly one `lightboxEnvironment` governs the complete scene and is identical in the top-level SceneSpec and direction constraints.
- [ ] The selected mode is one of `diffused_softbox`, `transmitted_light_table`, or `hybrid_diffused_table`, and its active table emitter/top fill states are coherent.
- [ ] The orthographic camera, radial center-to-edge falloff, frosted surface, diffuser layers, and frame occlusion match the environment contract.
- [ ] Metal is `opaque_reflective`, paper is `opaque_diffuse`, tracing paper is `translucent`, film is `transmissive`, and acrylic/glass is `refractive_highlight`; they do not share one generic plastic finish.
- [ ] Exact products, logos, and approved text remain `source_preserved` `exact_2d_layer` pixels.
- [ ] Contact shadows use the declared material-specific response and correspond to thickness and material.
- [ ] An unsupported material/environment combination blocks rendering instead of silently falling back.
- [ ] The environment records visual preset controls only; it contains no fabricated placement coordinates, object dimensions, or photometric-calibration claims.
- [ ] Scale-critical dimensions are evidenced or explicitly marked inferred/unknown.
- [ ] Generated props have plausible relative scale, thickness, contact, and non-intersection.
- [ ] Low-poly geometry is limited to suitable props and structures.
- [ ] Bloom, grain, and color grading remain restrained.

## Workflow Gates

- [ ] Manifest approval exists and matches the current manifest hash.
- [ ] The VisualDirection compiler received both the current manifest and the current human workflow receipt; neither artifact was inferred from the direction record.
- [ ] A reference-only project stopped before VisualDirection, scene creation, preview rendering, or final rendering.
- [ ] If a new concept was explicitly requested from references, only an offline `ConceptAssetBrief` was produced; the candidate was ingested as a new content asset and returned to the first human approval.
- [ ] The selected preview PNG, `PreviewEvidenceRecord`, and current scene hashes agree.
- [ ] A seven-item `PreviewQualityReviewRecord` exists for the selected pixels; no item is `fail`, and every warning is shown to the human approver.
- [ ] `hardFailures` is empty: no `NESTED_BACKGROUND_RECTANGLE`, `CORNER_THUMBNAIL_TEMPLATE`, `FLOATING_ASSET_PLANES`, `SINGLE_GENERIC_MATERIAL`, `PALETTE_FRAGMENTATION`, `NO_DOMINANT_MATERIAL_RELATION`, `REFERENCE_SCOPE_LEAKAGE`, `REPRESENTATION_AS_FLOATING_STICKER`, `LIGHTBOX_SPATIAL_RELATIONSHIP_LOST`, or `UNJUSTIFIED_ELEMENT_DOMINANCE` is visible; one pixel hard failure blocks the second human approval.
- [ ] Deterministic failures retain their exact code through compiler, bridge, CLI, and API: `REFERENCE_SCOPE_VIOLATION`, `REPRESENTATION_UNSUPPORTED`, `MATERIAL_FORM_MISMATCH`, `UNJUSTIFIED_GENERATED_ELEMENT`, or `LIGHTBOX_ENVIRONMENT_MISSING`.
- [ ] Any candidate with a hard failure must not enter public examples, README promotion, or release artwork.
- [ ] Codex visual observations remain separate from deterministic validation findings.
- [ ] Scene approval exists and matches the current scene, validation, preview-evidence, and preview-quality-review hashes.
- [ ] No blocking validation issue remains.
- [ ] Final rendering occurred after both approvals.

## Enhancement

- [ ] Enhancement was optional and explicitly selected.
- [ ] The enhancer received background/control layers only.
- [ ] Exact assets and exact text were recomposited after enhancement.
- [ ] Enhanced output did not alter approved geometry or silhouettes.

## Delivery Evidence

- [ ] Final PNG exists and opens successfully.
- [ ] Manifest, scene, validation, approvals, control layers, exact-layer map, and export metadata are retained.
- [ ] Output hashes are recorded.
- [ ] Any claim of physical realism distinguishes calibrated dimensions from visual-scale plausibility.
- [ ] No remote model, API, cloud service, or vendor SDK was called by this skill.
- [ ] Verification commands and test counts are reported.
- [ ] Known limitations are stated without claiming unverified correctness.
